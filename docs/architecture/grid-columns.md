# ستون‌های DataGrid و ثبات ترجمه

2026-10-20 · الگوی پیش‌فرض قابل‌توسعه برای گریدهای تازه و مهاجرت تدریجی مصرف‌کنندگان موجود، با استثنای ساده برای مواردی که پیچیدگی اضافه می‌کند. وضعیت مهاجرت در [دفتر وضعیت PAT](../../../documents/spec/patterns/implementation-status.md) ثبت می‌شود.

## تصمیم فعلی

React Compiler در این تغییر فعال نشده است. تنظیمات build و وابستگی‌های کامپایلر تغییر نکرده‌اند؛ مبنای این الگو همان React بدون کامپایلر و memoization دستی در مرزهای لازم است. فعال‌سازی کامپایلر و حذف عمومی `memo`، `useMemo` یا `useCallback` بخشی از این مهاجرت نیست.

تعریف ستون‌ها از نمایش جدول جدا می‌شود تا ترتیب، عنوان ترجمه و تنظیمات کارت در فایل مشخصی تغییر کند. مشترک‌کردن این ساختار به معنی انتقال سلول‌های دامنه به ui-kit نیست.

## سادگی، توسعه و استثنا

معیار انتخاب این الگو، خوانایی و امکان تغییر ستون‌ها با حفظ رفتار و کارایی است. تعداد فایل‌ها، hookها یا کامپوننت‌های نمونهٔ attachments الزام همهٔ گریدها نیست.

- برای ستون‌های دارای metadata ثابت و عنوان ترجمه‌شده، constants ویژگی همراه `useGridColumns` نقطهٔ شروع پیشنهادی است.
- گرید کوچک یا دارای عنوان و نمایش خاص می‌تواند مستقیماً `readonly GridColumn<T, Sort>[]` را در ماژول ستون‌ها یا hook موجود ویژگی بسازد. لازم نیست صرفاً برای استفاده از helper، یک hook واسط، نوع جنریک تازه یا `RecordCell` مشترک ساخته شود.
- سلول ساده می‌تواند متن یا JSX برگرداند. کامپوننت جدا زمانی مفید است که رفتار، اشتراک داده، بازاستفاده یا خوانایی آن را توجیه کند؛ `memo` برای همهٔ سلول‌ها اجباری نیست.
- ستون وابسته به مجوز یا وضعیت در ویژگی ترکیب می‌شود. برای نیاز تازه ابتدا از `cell`، ترکیب ستون‌ها و API موجود استفاده کنید؛ قابلیت مشترک فقط با نیاز واقعی به shared اضافه شود. برای یک مورد خاص، registry یا لایهٔ تنظیمات عمومی تازه نسازید.

اگر الگو تعداد واسطه‌ها را زیاد کند، وابستگی‌ها را مبهم کند یا هزینهٔ رندر ایجاد کند، راه ساده‌تر مجاز است. یک توضیح کوتاه کنار تعریف ستون‌ها یا در شرح تغییر، شامل دلیل و رفتارهای حفظ‌شده کافی است؛ این انتخاب نیازمند مجوز جداگانه یا سند جدید نیست. تکرار نیاز در چند صفحه، فرصتی برای بازبینی راه‌حل مشترک است، نه دلیل تعمیم زودهنگام.

این انعطاف مربوط به شیوهٔ ساخت ستون‌هاست. نوع‌های درست، دادهٔ به‌روز، مرز feature/shared، ترجمه، دسترس‌پذیری و رفتار موبایل/دسکتاپ همچنان حفظ می‌شوند. برای صفحهٔ موجود نیز فقط وقتی مهاجرت کنید که تغییر سود مشخصی دارد؛ یکسان‌شدن تعداد فایل‌ها هدف مهاجرت نیست.

## مسئولیت فایل‌ها

جدول زیر مسئولیت‌ها را در الگوی کامل نشان می‌دهد؛ برای موارد ساده فقط بخش‌های موردنیاز را استفاده کنید و ساختار فایل همان feature را رعایت کنید.

| بخش                                                  | مسئولیت                                                                             |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `ui/.../constants/*-columns.constants.ts` در feature | تعریف ثابت و `readonly` ستون‌ها: `id`، `headerKey`، `card`، عرض، تراز و `sortField` |
| `ui/.../types/*-columns.types.ts` در feature         | شناسهٔ ستون‌ها، کلیدهای مجاز ترجمه و گزینه‌های hook                                 |
| `ui/.../hooks/use-*-columns.tsx` در feature          | اتصال ترجمه و props زمان اجرا به تابع نمایش سلول                                    |
| `useGridColumns` در `@dukani/ui-kit`                 | تبدیل metadata به `readonly GridColumn<T, Sort>[]`                                  |
| کامپوننت سلول در feature                             | نمایش و رفتار دامنه؛ در صورت نیاز اشتراک پیش‌نویس همان ردیف                         |
| کامپوننت میزبان `DataGrid`                           | اتصال منبع داده، انتخاب و ستون‌ها به جدول                                           |

نوع مشترک `GridColumnDefinition<Id, HeaderKey, Sort>` تنظیمات `GridColumn` را با `id` تایپ‌شده و `headerKey` نگه می‌دارد؛ `header` و `cell` هنگام اجرا ساخته می‌شوند. تعریف‌ها JSX، ترجمهٔ ازپیش‌محاسبه‌شده یا state ردیف ندارند.

نمونهٔ واقعی در [ثابت‌های ستون انتخاب کالا](../../packages/features/product-entry/src/ui/attachments/constants/attachment-record-columns.constants.ts):

```ts
export const ATTACHMENT_RECORD_COLUMNS = [
  { id: 'title', headerKey: 'name', card: 'title', sortField: 'title' },
  { id: 'codes', headerKey: 'original' },
  { id: 'unit', headerKey: 'unit', card: 'control' },
  { id: 'membership', headerKey: 'membership', card: 'status' },
  { id: 'alias', headerKey: 'local', card: 'control' },
] as const satisfies readonly GridColumnDefinition<
  AttachmentRecordColumnId,
  AttachmentHeaderKey,
  AttachmentSort
>[];
```

جابه‌جایی ستون، تغییر عنوان، عرض یا محل آن روی کارت فقط metadata را تغییر می‌دهد. افزودن ستون با محتوای تازه، علاوه بر metadata، نیازمند تکمیل نوع شناسه و نمایش همان سلول است.

## تابع cell چه چیزی برمی‌گرداند؟

قرارداد `GridColumn.cell` برابر `(row: T) => ReactNode` است. تابع نمایش در hook ویژگی علاوه بر ردیف، شناسهٔ ستون را می‌گیرد:

```tsx
const renderCell = useCallback(
  (candidate: AttachmentCandidate, part: AttachmentRecordColumnId) => (
    <AttachmentRecordCell
      candidate={candidate}
      selection={selection}
      disabled={disabled}
      onChange={onChange}
      part={part}
    />
  ),
  [selection, disabled, onChange],
);

return useGridColumns({
  definitions: ATTACHMENT_RECORD_COLUMNS,
  translate: t,
  renderCell,
});
```

`renderCell` یک المان از کامپوننت ازقبل‌تعریف‌شده می‌سازد. تعریف کامپوننت یا فراخوانی `memo(...)` داخل hook انجام نمی‌شود؛ کامپوننت‌ها در سطح ماژول تعریف می‌شوند تا تغییر وابستگی‌ها هویت آن‌ها را عوض نکند.

اگر نمایش فقط به `row` و شناسهٔ ستون وابسته باشد، تابع نمایش در سطح ماژول کافی است؛ مانند [ستون‌های مرور و نتیجه](../../packages/features/product-entry/src/ui/attachments/hooks/use-attachment-summary-columns.tsx). اگر به props زمان اجرا وابسته باشد، مانند مثال بالا با `useCallback` و وابستگی‌های کامل ساخته می‌شود. وجود سلول تخصصی یا `memo` برای هر ستون الزامی نیست؛ متن ساده هم خروجی معتبر است.

`AttachmentRecordCell` در feature می‌ماند: با `useSyncExternalStore` وضعیت انتخاب همان کالا را می‌خواند و به محتوای سلول می‌دهد. `memo` این کامپوننت، بهینه‌سازی رندر والد است؛ جایگزین اشتراک در تغییرات پیش‌نویس نیست. `useGridColumns` هیچ شناختی از انتخاب واحد، بارکد یا مدل کالا ندارد.

## چه چیزی پایدار می‌ماند؟

[هوک مشترک](../../packages/shared/ui-kit/src/grid/use-grid-columns.ts) با `useMemo` و وابستگی‌های `[definitions, translate, renderCell]` ستون‌ها را می‌سازد. ثابت ماژولی برای `definitions` و تابع نمایش پایدار لازم‌اند تا این بهینه‌سازی در رندر عادی مؤثر باشد. تغییر ترجمه یا props مؤثر باید محتوای تازه بسازد؛ حذف وابستگی برای ثابت نگه‌داشتن ارجاع درست نیست.

[`useCatalogTranslations`](../../packages/shared/i18n/src/use-catalog-translations.ts) مترجم را بر اساس `locale` و شیء پیام‌های زبان فعال memo می‌کند. اگر wrapper کاتالوگ در هر فراخوانی تازه باشد ولی همان شیء پیام فعال را نگه دارد، به‌تنهایی مترجم تازه نمی‌سازد. تغییر زبان یا مرجع پیام‌های فعال، مترجم را به‌روز می‌کند. پیام‌ها را تغییرناپذیر نگه دارید و برای تغییر محتوا مرجع تازه بدهید.

ثبات `t` از باطل‌شدن بی‌دلیل memo ستون‌ها جلوگیری می‌کند؛ تضمین نمی‌کند کامپوننت مصرف‌کننده هرگز رندر نشود. state، context، اشتراک بیرونی یا سایر props همچنان می‌توانند رندر ایجاد کنند. `memo` نیز صرفاً بهینه‌سازی است و درستی داده نباید به cache آن وابسته باشد. [مرجع React برای memo](https://react.dev/reference/react/memo)

## دامنهٔ مهاجرت

- مرحلهٔ اول: ستون‌های `AttachmentRecords` و `AttachmentSummary`، زیرساخت `useGridColumns` و ثبات مترجم `useCatalogTranslations`.
- مرحلهٔ بعد در `product-entry`: بررسی همهٔ بخش‌ها و اعمال الگو در metadata، ردیف‌های قابل‌ویرایش و چرخهٔ پیش‌نمایش تصویر. استثناهای `RecordList` و جست‌وجوی cursor و دلیل حفظ فرم‌های موجود در [README ویژگی](../../packages/features/product-entry/README.md) ثبت شده‌اند. سایر گریدهای اپ هنوز مهاجرت نکرده‌اند.
- `CatalogItemGrid` (catalog، 2026-10-20): metadata در `catalog/src/ui/constants/catalog-item-columns.constants.ts`؛ سلول‌ها فقط به ردیف وابسته‌اند، پس renderer در سطح ماژول و بدون hook واسط است. `OpeningPickGrid` (purchasing) بررسی شد و تعریف مستقیم `GridColumn[]` با دلیل کنار کد ماند: هر سلول به مترجم و قالب‌بندهای زمان اجرا (`usePurchasePresentation`) وابسته است و metadata جدا فقط فایل و switch اضافه می‌کرد. با این دو، هر چهار مصرف‌کنندهٔ فعلی `DataGrid` بررسی شده‌اند.
- پس از آن: فهرست‌کردن باقی مصرف‌کنندگان `DataGrid` و مهاجرت موردی با همان بررسی‌ها. این سند ادعای مهاجرت کل اپ یا همهٔ hookهای ترجمه را ندارد.

## حفظ UI و کارایی

ریفکتور ستون‌ها نباید تجربهٔ کاربر یا کارایی را کاهش دهد. بررسی را متناسب با دامنهٔ تغییر انتخاب کنید و از آزمون‌های موجود استفاده کنید:

- تغییر نمایش یا تعامل: عنوان، ترتیب و محتوای ستون‌ها، کارت موبایل و جدول دسکتاپ، RTL و نام دسترس‌پذیر کنترل‌ها حفظ شوند. برای ورودی‌ها، مقدار، فوکوس و کار با کیبورد؛ برای گریدهای تعاملی، انتخاب، sort و حفظ پیش‌نویس بررسی شوند.
- تغییر ترجمه یا callback: تغییر زبان و پیام فعال و استفاده از وضعیت و callback جدید آزموده شود؛ ثبات مرجع نباید باعث نمایش دادهٔ قدیمی شود.
- تغییر memoization یا اشتراک داده: رندرهای ردیف‌های نامرتبط هنگام تایپ و انتخاب بررسی شوند. به‌روزرسانی بخش واقعاً وابسته، مثل شمارندهٔ انتخاب یا خلاصه، طبیعی است. شمارندهٔ رندر شواهد دامنهٔ رندر را می‌دهد، نه زمان پاسخ‌گویی یا مصرف حافظه را.
- تغییر پرهزینه یا مشاهدهٔ کندی: با داده، سناریو، دستگاه و تنظیمات یکسان، قبل و بعد را با Profiler یا اندازه‌گیری مرورگر مقایسه کنید؛ برای سنجش تجربهٔ نهایی از build تولید استفاده کنید. اگر افت معنادار دیده شد، همان تغییر اصلاح یا ساده شود؛ الگوی معماری توجیه افت نیست.

برای تغییر اجرایی، typecheck، lint، آزمون‌های مرتبط و بررسی معماری انجام شود؛ تغییر مشترک، بررسی مصرف‌کنندگان متأثر را هم می‌خواهد. اصلاح صرفاً مستندات به اجرای دوبارهٔ همهٔ تست‌ها یا بنچمارک تازه نیاز ندارد. برای ادعای سرعت بیشتر، اندازه‌گیری همان شاخص لازم است؛ جابه‌جایی فایل یا موفقیت تست‌ها به‌تنهایی شاهد افزایش سرعت نیست.

## اعتبارسنجی مرحلهٔ اول (attachments)

در 2026-10-20، بررسی‌های زیر روی این تغییر انجام شد:

- آزمون کامل بسته‌های `@dukani/i18n`، `@dukani/ui-kit` و `@dukani/product-entry`: به‌ترتیب ۷، ۲۰۹ و ۱۱۸ آزمون موفق.
- typecheck و lint هر سه بسته موفق؛ lint روی این دستگاه هشدار نبود cache گراف Nx دارد و قانون مرز ماژول Nx را رد می‌کند. بررسی مستقل `architecture:check` و `i18n:check` نیز بدون مشکل انجام شد.
- آزمون‌های رگرسیون، ثبات مرجع مترجم و ستون‌ها، به‌روزرسانی زبان و پیام‌ها، استفاده از callback جدید و حفظ هویت DOM، فوکوس و مقدار بارکد را پوشش می‌دهند. شمارندهٔ تست attachments ثبات wrapper سلول‌های نامرتبط از مسیر والد را بررسی می‌کند؛ رندر داخلی ناشی از اشتراک `useSyncExternalStore` را اندازه نمی‌گیرد.
- آزمون [AttachmentSummary](../../packages/features/product-entry/src/ui/attachments/tests/AttachmentSummary.test.tsx) برای ۱۰۰۰ ردیف، نمایش ۲۰ ردیف صفحهٔ دسکتاپ، مجموع کامل و دسترسی به صفحهٔ آخر را بررسی می‌کند؛ این آزمون زمان رندر را اندازه نمی‌گیرد.
- اسکریپت `tools/scripts/flow-catalog-attachments.mjs` در مرورگر واقعی با عرض‌های ۳۹۰ و ۱۴۴۰ پیکسل موفق بود: انتخاب، ویرایش بارکد، حفظ پیش‌نویس هنگام تغییر فیلتر، مرور، نتیجهٔ جزئی، تعارض بارکد، refresh و ورود به اصلاح موارد ناموفق. ارسال مجدد در این سناریوی مرورگر کامل نمی‌شود؛ محدودشدن پیش‌نویس به موارد ناموفق جداگانه در [آزمون جریان پیوست](../../packages/features/product-entry/src/application/catalog-attachment-workflow.test.ts) آزموده شده است.

شاهد آزمون‌ها: [ثبات مترجم](../../packages/shared/i18n/src/use-catalog-translations.test.tsx)، [ستون‌ها و callback](../../packages/shared/ui-kit/src/grid/use-grid-columns.test.tsx)، [تعامل و رندر سلول‌ها](../../packages/features/product-entry/src/ui/attachments/tests/AttachmentRecords.test.tsx) و [سناریوی مرورگر](../../tools/scripts/flow-catalog-attachments.mjs). تصاویر مرورگر در مسیر محلی و gitignoredِ `front/tmp/f10-02-qa/` ذخیره و بازبینی شدند؛ برای تولید دوباره از همان اسکریپت استفاده شود.

در سناریوهای بررسی‌شده مشکل UI مشاهده نشد و آزمون‌های ثبات مرجع و wrapper موفق بودند. بررسی مرورگر با `NEXT_PUBLIC_API_MODE=mock` انجام شد؛ این نتیجه، تأیید API واقعی یا build تولید نیست. مقایسهٔ پیکسلی تصاویر قبل/بعد و مقایسهٔ عددی قبل/بعد برای زمان رندر، پاسخ‌گویی، حافظه یا اندازهٔ bundle انجام نشده؛ بنابراین نتیجه تضمین نبود افت کارایی یا تغییر ظاهری در همهٔ شرایط نیست. کامپایلر فعال نشده و عملکرد آن اندازه‌گیری نشده است.

نتیجهٔ بازبینی بعدی کل `product-entry`، آزمون‌های ردیف‌های قابل‌ویرایش و سناریوهای مرورگر در [README ویژگی](../../packages/features/product-entry/README.md) ثبت شده‌اند؛ شمار آزمون‌های بالا مربوط به مرحلهٔ اول است.

## تصمیم آینده دربارهٔ React Compiler

کامپایلر می‌تواند memoization را خودکار کند، اما React برای حذف memoization موجود بررسی و آزمون را توصیه می‌کند. سازگاری کد با Rules of React نیز در تصمیم فعال‌سازی مؤثر است. [راهنمای React Compiler](https://react.dev/learn/react-compiler/introduction)

فعال‌سازی سراسری در Next می‌تواند هزینهٔ build اضافه کند؛ اثر واقعی آن برای این مخزن در این برش اندازه‌گیری نشده است. با تصمیم بعدی کاربر، ابتدا یک دامنهٔ محدود انتخاب شود و build، رندر، فرم‌ها، selection store و virtualizer در آن بررسی شوند؛ سپس دامنه توسعه پیدا کند. فعال‌بودن `reactStrictMode` به معنی فعال‌بودن کامپایلر نیست. [تنظیم reactCompiler در Next.js](https://nextjs.org/docs/app/api-reference/config/next-config-js/reactCompiler)
