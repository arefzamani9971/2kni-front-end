# وضعیت پیاده‌سازی بک‌اند دکانی

آخرین به‌روزرسانی: ۱۴۰۵/۰۷/۰۵ (۲۷ سپتامبر ۲۰۲۶)، صبح، به وقت تهران

> کد در این محیط **کامپایل نشده** است، چون NuGet و SDK دات‌نت در دسترس نیستند. بعد از هر مرحله دو بررسی ایستا اجرا می‌شود:
> - `check_references.py`: دیده‌شدن نوع‌ها، `using`ها و reference پروژه‌ها؛
> - `gen_openapi.py`: route تکراری، نوع ناشناخته، و تطابق هر Controller با سرویسش.
>
> وضعیت فعلی: **هر دو بررسی بدون خطا**.
>
> **روش کار از این به بعد:** هر بار فقط یک agent اجرا می‌شود. بعد از تمام‌شدن هر agent، این فایل به‌روز و در git کامیت می‌شود و بعد بخش بعدی شروع می‌شود. مخزن git در همین پوشه ساخته شده (کامیت پایه: `292c5b3`).

## تصمیم‌های این مرحله

| موضوع | تصمیم |
|---|---|
| نقش‌ها | یک حساب برای هر شماره موبایل. ادمین نقش پلتفرمی دارد، فروشنده با عضویت در فروشگاه مشخص می‌شود، و مشتری از روی موبایل تأییدشده با OTP |
| پیامک | کاوه‌نگار (verify/lookup)، به‌علاوه حالت Fake که فقط لاگ می‌کند |
| فایل | MinIO؛ لینک دانلود موقت و امضاشده است |
| اعتبارسنجی | FluentValidation با فیلتر سراسری؛ خطاها ۴۰۰ با کد `VALIDATION_FAILED` و پیام فارسی برای هر فیلد |
| سفارش مشتری (۳.۰) | ورود با QR فروشگاه. تحویل به چهار روش: داخل فروشگاه، تحویل حضوری با تأیید و تعیین زمان توسط فروشگاه، پیک فروشگاه، پست بین‌شهری |
| پرداخت سفارش | نقد، کارتخوان، چک و کارت‌به‌کارت (با فیش اجباری که فروشنده تأیید می‌کند)، به‌علاوه بیعانه. فعلاً درگاه آنلاین نداریم |

## کارهای باز بین ماژول‌ها

1. پروژه‌های تست باید به `Dukani.slnx` اضافه شوند. این کار در مرحله آخر انجام می‌شود.
2. Migration وجود ندارد. روی سیستم خودتان `dotnet ef migrations add Initial` اجرا کنید. ستون‌ها و ایندکس‌های جدید این مرحله هم در همین Migration می‌آیند.
3. ✅ **بعد از اصلاح بهای رسید خرید:** میانگین بها در Inventory دوباره حساب می‌شود. ردیف‌های فاکتوری که بهایشان نامعلوم بوده بهای جدید را می‌گیرند (بهای معلوم هرگز بازنویسی نمی‌شود) و روزهای گزارش دوباره حساب می‌شوند. **نکته:** در Worker باید `AddSalesModule()` قبل از `AddReportingModule()` بماند.
4. ✅ **صفحه بازبینی خروج کارمند:** پیش‌نویس‌های فروش و خرید شمرده و منتقل می‌شوند. اقدام‌های مرکز اقدام هنوز مسئول ندارند.
5. ✅ متن پایین فاکتور (`InvoiceFooterText`) به تنظیمات فروشگاه اضافه شد.
6. ورود Excel برای مشتری‌ها و تغییر گروهی قیمت (نسخه ۱.۱) هنوز پیاده نشده است.
7. **سفارش:** فرانت باید خطای ۴۰۹ `ORDER_VERSION_STALE` را مدیریت کند. تصویر فیش پیش از commit تراکنش ذخیره می‌شود، پس در صورت rollback یک فایل بی‌صاحب می‌ماند. `RefundObligationRials` بازپرداخت‌های پرداخت‌شده را هم می‌شمارد؛ شاید عدد «مانده بازپرداخت» هم لازم باشد.
8. **پنل مشتری:**
   - در مسیرهای پنل، «امروز» برای صورت‌حساب به وقت تهران حساب می‌شود.
   - مرجع کارت‌به‌کارت با فیش‌های سفارش (Ordering) مقایسه نمی‌شود.
   - ✅ درخواست تسویه جدید فوراً در مرکز اقدام فروشنده ظاهر می‌شود.
   - اگر تسویه با خطای غیرمنتظره گیر کند، تا تکرار موفق «تأیید»، درخواست قابل رد نیست.
9. **گزارش‌ها:**
   - ✅ هشدار کمبود بر اساس موجودی قابل فروش (موجودی منهای رزرو) است.
   - مبلغ نسیه فروش، پرداخت‌هایی را که بعداً برگشت خورده‌اند هم شامل می‌شود.
   - فایل خروجی‌های منقضی‌شده از MinIO پاک نمی‌شود.

## تاریخچه

- **مرحله ۱:** زیرساخت مشترک ساخته شد (اعتبارسنجی، پیامک، فایل، دسترسی Storefront، پورت‌های رزرو و فاکتور سفارش).
- **مرحله ۲:** Identity، Stores، Catalog، Admin، Inventory، Customers، Sales، Purchasing و Imports کامل شدند. Reporting، Ordering و CustomerPortal به محدودیت موقت API خوردند.
- **مرحله ۳ (بازبینی بعد از توقف):** وضعیت از روی فایل‌ها بررسی شد. Reporting نوشته شده ولی تأیید نهایی ندارد. Ordering بدون تست و بدون مرور نهایی مانده. CustomerPortal بدون سرویس و Controller مانده. مخزن git ساخته و کامیت پایه ثبت شد.

- **مرحله ۴:** Ordering کامل شد: مرور کامپایل و منطق، ۶ اصلاح، و پروژه تست.
- **مرحله ۵:** CustomerPortal کامل شد: ۶ سرویس، ۲۲ endpoint، Validatorها و تست‌ها.
- **مرحله ۶:** بازبینی Reporting (پس از یک وقفه به‌خاطر محدودیت API) کامل شد: یک اصلاح و تست‌های Validator.
- **مرحله ۷:** Docker و استقرار. `appsettings` امن شد: کلید JWT پیش‌فرض حذف شد و مقادیر توسعه به `appsettings.Development.json` رفت. بسته Seed به پوشه `seed/` مخزن منتقل شد.
- **مرحله ۸ (بازبینی الف):** ۵ اشکال رفع شد:
  - `using` جاافتاده در `OperationsController`، که خطای قطعی build بود؛
  - دو ویژگی فقط‌خواندنی در Catalog که EF آن‌ها را رابطه اضافه فرض می‌کرد؛
  - و سه مورد احتیاطی دیگر.
  
  همچنین همه `SqlQuery<scalar>`ها (شماره‌گذاری، تنظیمات فروشگاه، قفل سفارش، شمارش کالا) به helper جدید `QueryScalarsAsync` منتقل شدند. این helper به نام ستون `"Value"` وابسته نیست، پس با قاعده نام‌گذاری snake_case تداخل ندارد.
- **مرحله ۹ (بازبینی ب):** یک خطای قطعی build رفع شد (`ImportColumns`: ثابت و متد هم‌نام، CS0102). دو مورد مقاوم‌سازی هم انجام شد: قید generic در مبدل JSON، و جلوگیری از خطای ۵۰۰ روی تاریخ خراب در فایل Excel. شکاف میانگین بها پس از اصلاح یا ابطال خرید هم پر شد: بازپخش تاریخچه رسیدها در Inventory، به‌علاوه ۴ تست جدید.
- **مرحله ۱۰ (بازبینی ج):** خطای کامپایل، راه‌اندازی یا SQL پیدا نشد. همه ستون‌های SQL گزارش‌ها با اسکریپت تطبیق داده شدند.
  - یک اشکال مدل رفع شد: دو ایندکس بی‌نام یکسان روی فاکتورها، که EF یکی‌شان را حذف می‌کرد.
  - `ProductCostChanged` در Sales و Reporting پیاده شد، با تست.
  - سؤال باز کسب‌وکاری: در گزارش روزانه، «مبلغ پرداخت‌شده هنگام فروش» تخصیص‌های برگشت‌خورده (مثل چک برگشتی) را هم حساب می‌کند.
- **مرحله ۱۱ (بازبینی د):** خطای قطعی پیدا نشد. شش تغییر احتیاطی انجام شد: عبارت مجموعه در شرط، مقایسه‌های nullable در Validatorها، انتساب tuple، `Contains` روی List به جای آرایه در کوئری EF، ارجاع ASP.NET در پروژه تست، و یک assert مبهم.
- **مرحله ۱۲:** شکاف‌های بین ماژولی بسته شد و تغییرات API فقط اضافه‌شدنی بود (`CustomerMergePreviewDto`، `LowStockItemDto`، `StoreSettingsDto`).
  - ادغام مشتری در CustomerPortal درخواست‌های تسویه را هم منتقل می‌کند.
  - مستندات دوباره ساخته شد و سند معماری و README به‌روز شدند.
